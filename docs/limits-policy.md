# Лимитная политика T-Invest API

Документ фиксирует лимиты из официальной страницы T-Invest API:
<https://tinkoff.github.io/investAPI/limits/>

Актуальность данных зависит от политики брокера. При изменении официальной документации этот файл нужно обновить.

## Что важно учитывать

- Лимиты считаются суммарно по всем методам внутри каждого сервиса.
- Лимитная политика распространяется на все счета пользователя.
- При превышении лимита API возвращает ошибку.
- Отдельно упоминается ограничение по IP: превышение не происходит, если число запросов с одного IP не выше `1000` в минуту.

## Лимиты unary-методов

Для этого SDK важнее всего лимиты `gRPC`, так как пакет работает через `nice-grpc`. Для полноты ниже приведены и `REST`-значения из официальной таблицы.

| Сервис или метод | gRPC в минуту | REST в минуту |
| --- | ---: | ---: |
| Сервис инструментов | 200 | 100 |
| Сервис счетов | 100 | 50 |
| Сервис операций | 200 | 100 |
| Формирование отчетов в сервисе операций | 5 | - |
| Сервис котировок | 300 | 150 |
| `getHistory` | - | 30 |
| Сервис стоп-ордеров | 50 | 25 |
| Песочница | 200 | 100 |
| Сервис ордеров | 100 | 50 |
| `getOrders` | 200 | 100 |
| `postOrder` | 300 | 150 |
| `cancelOrder` | 100 | 50 |

## Лимиты stream-соединений

У пользователя есть 5 лимитных грейдов. Они зависят от количества выставленных заявок и процента их исполнения.

| Грейд | MarketData stream | Orders stream | Operations stream |
| --- | ---: | ---: | ---: |
| 1 | 2 | 1 | 1 |
| 2 | 4 | 1 | 1 |
| 3 | 5 | 1 | 1 |
| 4 | 16 | 1 | 1 |
| 5 | Без ограничений | 1 | 1 |

Дополнительные ограничения:

- В одном `MarketData` stream можно держать не более `300` одновременных подписок суммарно на свечи, стаканы и ленту обезличенных сделок.
- Подписки `Info` на торговые статусы в этот лимит не входят.
- Метод запроса тарифа пользователя может вернуть лимит stream-соединений на `1` больше для безопасного переподключения. Официальная рекомендация: не упираться в максимальное значение.
- Счетчик stream-соединений обновляется каждые `2` минуты.

## Как формируется лимитный грейд

Грейд пересчитывается раз в сутки после окончания торгов на основе статистики заявок за последние `30` дней.

- Если пользователь не выставлял заявки через T-Invest API, у него будет грейд `1`.
- Чтобы грейд пересчитывался, нужно выставить хотя бы одну заявку в месяц.
- Лимита на количество активных заявок нет.

Матрица грейдов из официальной документации:

| Количество исполненных заявок | Исполнение > 50% | Исполнение > 10% | Исполнение > 2% | Исполнение < 2% |
| --- | ---: | ---: | ---: | ---: |
| меньше 10 | 1 | 1 | 1 | 1 |
| меньше 200 | 2 | 2 | 2 | 1 |
| меньше 1 000 | 4 | 3 | 2 | 1 |
| меньше 5 000 | 5 | 4 | 3 | 1 |
| меньше 10 000 | 5 | 5 | 4 | 2 |
| больше 10 000 | 5 | 5 | 4 | 2 |

## Как это связано с SDK

SDK поддерживает локальный throttling unary-запросов через опцию `trackLimits`, которая включена по умолчанию.

Что делает SDK сейчас:

- ограничивает только unary-вызовы;
- использует локальную таблицу лимитов по сервисам;
- не управляет stream-лимитами;
- не обновляет лимиты автоматически через `users.getUserTariff()`.

Практические рекомендации:

- для торговых сценариев не полагайтесь только на локальный throttling SDK;
- учитывайте отдельные лимиты для `postOrder`, `cancelOrder` и `getOrders`;
- учитывайте, что лимиты пользователя могут отличаться по stream-грейду;
- при высокой нагрузке полезно запрашивать текущий тариф через `users.getUserTariff()`.
