# Политика именования

> Type: Policy. Здесь собраны правила именования сущностей в коде.

## Цель

Имена в коде должны быть единообразными, предсказуемыми и не создавать ложных смысловых сигналов.

Нотация имени должна отражать роль сущности, а не личное предпочтение автора.

## Базовые правила именования

В TypeScript/JavaScript-коде:

- `camelCase` - переменные, функции, значения, экспортируемые константы;
- `PascalCase` - классы, типы, интерфейсы, перечисления;
- `kebab-case` - имена, используемые во время выполнения, и имена файлов;
- `SCREAMING_SNAKE_CASE` / `ALL_CAPS` - запрещено для внутренних идентификаторов проекта.

Примеры:

```ts
const maxRetryCount = 3;

export const defaultConfig = {
  // ...
};

export function createSdkMetadata() {
  // ...
}

type UnaryLimits = Record<string, TInvestUnaryLimit>;

interface TInvestOptions {
  // ...
}

class TInvestNodeSDK {
  // ...
}
```

## Запрет `ALL_CAPS` / `SCREAMING_SNAKE_CASE`

Во внутреннем TypeScript/JavaScript-коде запрещено использовать `ALL_CAPS` / `SCREAMING_SNAKE_CASE` для имен TypeScript/JavaScript-идентификаторов.

Запрет распространяется на:

- локальные переменные;
- экспортируемые константы;
- функции;
- классы;
- типы;
- интерфейсы;
- члены перечислений;
- переменные реестров, обработчиков разрешения и таблиц сопоставления.

Запрещено:

```ts
export const DEFAULT_CONFIG = {};
export const UNARY_LIMITS = {};

const MAX_RETRY_COUNT = 3;

enum Status {
  ACTIVE = 'active',
  DISABLED = 'disabled'
}
```

Допустимо:

```ts
export const defaultConfig = {};
export const unaryLimits = {};

const maxRetryCount = 3;

enum Status {
  Active = 'active',
  Disabled = 'disabled'
}
```

Сам по себе `export const` не требует `ALL_CAPS`.

Даже если значение не изменяется после объявления, имя должно оставаться в `camelCase`, если это внутренняя сущность проекта.

## Symbolic codes

Строковые коды могут использовать `SCREAMING_SNAKE_CASE`, если это стабильные машинные коды, а не имена переменных, функций, классов или имена, используемые во время выполнения.

Допустимые случаи:

- коды ошибок приложения;
- машинные диагностические коды;
- коды совместимости;
- коды внешних протоколов или статусов;
- значения сгенерированных перечислений или формата обмена данными;
- строковые контракты между слоями приложения, внешние по отношению к конкретному слою.

Допустимо:

```ts
export type SdkErrorCode =
  | 'UNKNOWN_UNARY_LIMIT';

const sdkErrorMessages: Record<SdkErrorCode, string> = {
  'UNKNOWN_UNARY_LIMIT': 'Unhandled unary limits'
};
```

Запрещено:

```ts
const UNKNOWN_UNARY_LIMIT = 'Unhandled unary limits';
const SDK_ERROR_MESSAGES = {};
```

Используйте `SCREAMING_SNAKE_CASE` в строковом значении только для осознанного стабильного кода, а не вместо обычного имени.

Хорошее правило:

```text
ALL_CAPS identifier  -> запрещено
ALL_CAPS string code -> допустимо, если это stable symbolic code
```

В объектном литерале с ключами в виде машинных кодов предпочтительно явно писать ключи в кавычках. Это подчёркивает строковый контракт, а не стиль именования идентификатора.

## Исключения

Используйте `ALL_CAPS` только для имён из внешнего контракта, но не для внутренних имён проекта.

Допустимые исключения:

- переменные окружения;
- внешние поля протоколов и API;
- имена, требуемые сторонней библиотекой;
- сгенерированный код из proto;
- значения SQL, CLI или формата обмена данными;
- значения, которые должны дословно совпадать с внешним контрактом.

Примеры допустимых исключений:

```ts
process.env.NODE_ENV;
process.env.INVEST_TOKEN;
```

```ts
const envName = 'INVEST_TOKEN';
```

```ts
const externalPayload = {
  API_KEY: valueFromExternalSystem
};
```

Исключение действует, только когда `ALL_CAPS` требует внешняя система.

Не используйте `ALL_CAPS` только потому, что значение — константа.

## Object properties

Внутренние свойства объектов пишутся в `camelCase`.

Допустимо:

```ts
const options = {
  maxRequests: 100,
  useSsl: true
};
```

Запрещено:

```ts
const options = {
  MAX_REQUESTS: 100,
  USE_SSL: true
};
```

Исключение действует только для внешних данных, структур формата обмена или контрактов сторонних систем.

## Enum members

В написанных вручную перечислениях члены нужно называть в `PascalCase`.

Допустимо:

```ts
enum RuntimeMode {
  Production = 'production',
  Test = 'test'
}
```

Запрещено:

```ts
enum RuntimeMode {
  PRODUCTION = 'production',
  TEST = 'test'
}
```

Члены сгенерированных перечислений могут сохранять форму внешнего proto-контракта. Их нельзя переименовывать вручную.

Если внешнее значение должно быть `ALL_CAPS`, оно должно быть значением перечисления, а не именем его члена:

```ts
enum ExternalStatus {
  Active = 'ACTIVE',
  Disabled = 'DISABLED'
}
```

## Runtime-имена

Правила TypeScript-идентификаторов не распространяются на имена, используемые во время выполнения, и имена файлов.

Для них предпочтителен `kebab-case`.

Допустимо:

```ts
const serviceName = 'market-data-service';
const optionName = '--track-limits';
```

Запрещено использовать имя `ALL_CAPS` во время выполнения без внешней необходимости:

```ts
const serviceName = 'MARKET_DATA_SERVICE';
```

## Сгенерированный код

Сгенерированный код может нарушать эту политику, если такое имя пришло из proto-контракта или генератора кода.

Запрещено:

- вручную переименовывать сгенерированные сущности;
- применять политику к сгенерированным файлам как к написанному вручную коду;
- менять сгенерированные имена без изменения исходного контракта и процесса генерации.

Для написанных вручную обёрток вокруг сгенерированного кода нужно соблюдать обычные правила именования.

## Запрет переименований без задачи

Эта политика сама по себе не разрешает массовые переименования.

Переименовывайте сущность, только если:

- оно прямо требуется задачей;
- оно устраняет нарушение этой политики;
- изменение минимально необходимо;
- поведение программы не меняется.

Нельзя использовать эту политику как повод для сопутствующей очистки, рефакторинга или изменения архитектуры.

## Проверка

Ревью должно блокировать нарушения этой политики.

## Краткое правило

Внутренние имена проекта не используют `ALL_CAPS`.

`ALL_CAPS` допустим только во внешних контрактах, где такую форму требует внешняя система, а также в сгенерированном коде, который воспроизводит внешний контракт.
