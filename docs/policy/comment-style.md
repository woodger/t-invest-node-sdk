# Политика комментариев

> Type: Policy. Здесь собраны правила для комментариев в production-коде.

## Назначение

Комментарии должны объяснять роль модуля, границы ответственности, инварианты и причины неочевидных решений.

Комментарий не должен дублировать код, пересказывать очевидную механику или заменять ясные имена функций, типов и переменных.

Главный вопрос для комментария:

> Почему это решение существует именно в таком виде?

А не:

> Что делает эта строка?

## Базовые правила

1. В production-модуле, который участвует в runtime, задаёт контракт слоя или содержит нетривиальную ответственность, можно использовать один верхний архитектурный блок.
2. Верхний архитектурный блок должен описывать роль файла, допустимую ответственность, границы модуля и чужую ответственность, которую нельзя переносить в этот файл.
3. Добавляйте локальные комментарии только там, где без них теряется причина решения, инвариант или ограничение.
4. Очевидные действия кода комментировать не нужно.
5. JSDoc для публичных контрактов должен быть коротким и предметным.
6. Основной язык комментариев — русский. Сохраняйте единый язык и стиль в пределах файла. Имена API, идентификаторы и устойчивые технические термины переводить не нужно.
7. Комментарий должен объяснять "почему" или "зачем", а не пересказывать "что делает строка".
8. Комментарий не должен расширять контракт кода. Любая упомянутая в нём гарантия, инвариант, порядок выполнения, мера безопасности или ограничение должны подтверждаться кодом, типами или тестами.
9. История рефакторинга не должна храниться в комментариях. Для этого есть git, ADR и design notes.

## Верхний архитектурный блок

Верхний блок описывает модуль целиком, а не отдельные функции.

Шаблон:

```ts
/**
 * Модуль <роль файла в системе>.
 *
 * Здесь допустимы:
 * - <ответственность 1>;
 * - <ответственность 2>;
 * - <ответственность 3>;
 *
 * Здесь не должно быть <чужая ответственность>.
 */
```

Хороший пример:

```ts
/**
 * Модуль SDK internals собирает gRPC channel, metadata и middleware.
 *
 * Здесь допустимы:
 * - создание low-level nice-grpc primitives;
 * - wiring unary middleware;
 * - преобразование SDK options в runtime dependencies;
 *
 * Здесь не должно быть generated service logic или public package exports.
 */
```

Плохой пример:

```ts
/**
 * Файл для SDK.
 */
```

Такой комментарий не объясняет роль модуля, его границы и допустимую ответственность.

## Исключения

Верхний архитектурный блок не обязателен для:

- `index.ts` / barrel export файлов;
- generated-файлов;
- test fixtures;
- тривиальных файлов с одним очевидным типом или константой;
- временных локальных helper-файлов, не задающих production-контракт.

Если в таком файле есть верхний блок, он должен быть содержательным.

## JSDoc публичных контрактов

JSDoc публичных функций, классов и интерфейсов должен описывать только contract-level детали:

- входные ограничения;
- side effects;
- ошибки;
- lifecycle;
- важные гарантии;
- ограничения внешнего API.

JSDoc не нужен, если смысл полностью ясен из имени, типов и кода.

Плохо:

```ts
/**
 * Создает metadata.
 */
createSdkMetadata(...)
```

Лучше:

```ts
/**
 * Создает metadata для всех SDK clients.
 * Authorization всегда передается как Bearer token, x-app-name добавляется только при явной настройке.
 */
createSdkMetadata(...)
```

Но если это уже очевидно из интерфейса и тестов, комментарий лучше не добавлять.

## Когда комментарий нужен

Комментарий нужен, если он объясняет:

- роль модуля;
- границу слоя;
- неочевидный инвариант;
- workaround;
- ограничение внешнего API;
- причину необычной ветки;
- причину cleanup-логики;
- сохранение совместимости со старым контрактом;
- намеренно пустую ветку, если отсутствие действия является частью логики;
- placeholder / TODO с объяснением, почему реализации пока нет;
- причину, почему зависимость допустима именно здесь.

Хорошо:

```ts
// Stream calls не проходят через unary limiter:
// лимиты stream-соединений управляются отдельной политикой API.
if (call.responseStream) {
  return call.next(call.request, options);
}
```

Хорошо:

```ts
// Первый unary-запрос не задерживается:
// limiter ограничивает интервал между последовательными вызовами.
if (lastCallTime === undefined) {
  lastCallTime = now;
  return;
}
```

## Когда комментарий не нужен

Комментарий не нужен, если:

- смысл уже ясен из имени функции, типа и кода;
- комментарий повторяет строку буквально;
- комментарий описывает тривиальную механику;
- комментарий объясняет синтаксис языка;
- комментарий устаревает быстрее, чем сам код;
- комментарий хранит историю изменений вместо актуальной причины решения.

Плохо:

```ts
// Create metadata
const metadata = createMetadata();
```

Плохо:

```ts
// Check if path exists
if (limits[path] !== undefined) {
  return limits[path];
}
```

## TODO и placeholder

TODO допустим только если он объясняет:

- почему реализация отложена;
- какое ограничение сейчас действует;
- при каком условии к этому месту нужно вернуться.

Хорошо:

```ts
// TODO: stream limit tracking требует данных users.getUserTariff().
// Вернуться при добавлении runtime tariff refresh.
```

Плохо:

```ts
// TODO: fix later
```

Явно объясняйте намеренно пустой модуль или ветку.

## Workaround-комментарии

Workaround-комментарий должен называть внешнее ограничение и объяснять выбранный совместимый механизм.

Хорошо:

```ts
// nice-grpc ожидает AsyncIterableIterator даже для unary middleware,
// поэтому unary response возвращается через минимальный iterator wrapper.
return iterator;
```

Плохо:

```ts
// Return iterator
return iterator;
```

## Комментарии и архитектурные границы

Комментарий полезен, когда он защищает границу слоя.

Хорошо:

```ts
/**
 * Модуль infrastructure adapter преобразует SDK options в gRPC runtime dependencies.
 *
 * Здесь допустимы:
 * - создание channel;
 * - создание metadata;
 * - подключение middleware;
 *
 * Здесь не должно быть public API exports или generated DTO mutation.
 */
```

Такой блок помогает не смешивать adapter, generated code и public SDK API.

## Комментарии и тесты

Комментарии не заменяют тесты.

Важный инвариант из комментария желательно защитить тестом.

Например, если комментарий говорит, что stream calls не проходят через unary limiter, это должно быть проверено тестом middleware behavior.

## Практика применения

1. Сначала писать ясный код.
2. Затем добавлять комментарий только там, где без него теряется причина решения.
3. При ревью удалять шумные комментарии так же уверенно, как мертвый код.
4. После рефакторинга проверять комментарии на актуальность.
5. Не переносить историю изменений в кодовые комментарии.
6. Не использовать комментарий как оправдание плохого имени или размытой ответственности модуля.

## Критерий хорошего комментария

Хороший комментарий помогает понять:

- почему модуль существует;
- где его границы;
- какой инвариант нельзя нарушать;
- какое внешнее ограничение повлияло на код;
- почему очевидно странное решение на самом деле намеренное.

Если комментарий можно удалить без потери смысла, его нужно удалить.
