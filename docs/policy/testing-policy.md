# Политика тестирования

> Type: Policy. Здесь собраны требования к тестируемости, структуре и именованию тестов.

## Назначение

Тесты должны защищать контракты рабочего кода, наблюдаемое поведение и граничные сценарии SDK.

Тест не должен закреплять случайную реализацию, временную структуру кода или внутренний порядок действий, если публичный контракт их не определяет.

Главный вопрос для теста:

> Какое поведение проверяет этот тест или какую ошибку в работе SDK он помогает предотвратить?

А не:

> Какие строки кода были выполнены?

## Как запускать тесты

Тесты пишутся на TypeScript в `src/**/*.test.ts` и используют стандартные модули Node.js:

- `node:test`;
- `node:assert`.

Перед запуском тестов после изменений в `src` нужно пересобрать проект:

```bash
npm run build
npm test
```

`npm run build` — обязательная проверка компиляции. Она должна проходить с текущим `tsconfig.json`: при ошибках типизации исправляйте исходный код или тесты, а не ослабляйте TypeScript-конфигурацию без отдельного решения.

`npm test` запускает скомпилированные тесты через внешний инструмент `fwa`:

```bash
fwa --prune
```

Инструмент `fwa`:

- читает `rootDir` и `outDir` из `tsconfig.json`;
- рекурсивно собирает скомпилированные тесты из `dist`;
- удаляет скомпилированные тесты без соответствующего исходного файла через `--prune`;
- останавливает запуск, если скомпилированный тест старше своего исходного файла;
- делегирует выполнение стандартному `node:test`;
- запускает тестовые файлы в отдельных процессах.

Если `npm test` сообщает, что скомпилированные тесты старше исходных файлов, выполните `npm run build` и повторите запуск. Удаление скомпилированных тестов без исходных файлов — штатное поведение `fwa --prune`.

## Обязательность тестов

Любой переиспользуемый код должен иметь тесты.

Тесты обязательны для:

- общих модулей;
- внутренних механизмов SDK;
- middleware;
- логики ограничителя unary-запросов;
- разбора данных;
- проверок данных;
- адаптеров к внешним API;
- работы с файловой системой;
- переиспользуемой логики приложения;
- ветвей кода с несколькими допустимыми или ошибочными сценариями.

Код должен быть покрыт тестами, если его вызывают из нескольких мест, если он образует границу между слоями или нормализует внешние данные.

## Что обязательно тестировать

Обязательно тестируйте:

- публичное поведение `TInvestNodeSDK`;
- создание метаданных, канала и типизированных клиентов;
- поведение middleware для unary- и потоковых вызовов;
- ограничитель unary-запросов и выбор квот;
- преобразование конфигурации в поведение при выполнении;
- вспомогательные функции проверки данных;
- граничные случаи, которые могут привести к незаметному повреждению данных;
- регрессионные сценарии, которые уже ломались или выглядят хрупкими;
- поведение сценария запуска тестов, если оно реализовано в коде проекта.

## Что обычно не требует отдельного теста

Обычно не нужно выносить в отдельные тесты:

- одноразовую склейку вызовов без собственной логики;
- простое делегирование без ветвлений;
- простую передачу аргументов без нормализации или преобразования между контрактами;
- приватную вспомогательную функцию, если её поведение полностью проверяется через публичный API;
- стандартный код фреймворка без собственной логики проекта;
- сгенерированный код из `src/generated`.

Тест можно не писать, только если у кода действительно нет собственного поведения. Ветвление, нормализация, резервный сценарий, преобразование ошибки или нестандартный граничный случай требуют теста.

## Требования к тестам

Тесты должны быть:

- изолированными;
- детерминированными;
- читаемыми;
- минимальными, но достаточными;
- сфокусированными на одном поведении;
- ориентированными на наблюдаемый результат, а не на внутреннюю реализацию.

Один тест должен проверять одно поведение.

В одном тесте может быть несколько проверок одного контракта. Если они проверяют разные причины изменения поведения, разделите их на отдельные тесты.

## Граница тестового файла

Тестовый файл должен покрывать конкретный файл рабочего кода, а не директорию.

Правило соответствия:

```text
src/bootstrap/cli/help.ts           -> src/bootstrap/cli/help.test.ts
src/bootstrap/cli/registry.ts       -> src/bootstrap/cli/registry.test.ts
src/bootstrap/cli/runner.ts         -> src/bootstrap/cli/runner.test.ts
src/bootstrap/cli/version.ts        -> src/bootstrap/cli/version.test.ts
```

Запрещено создавать тест, который по имени выглядит как тест директории или barrel-модуля:

```text
src/bootstrap/cli.test.ts           # покрывает директорию cli/
src/bootstrap/cli/index.test.ts     # покрывает barrel-only index.ts
```

Исключение действует только для точки запуска или точки входа пакета с собственным поведением. Такой тест должен проверять саму точку входа, а не внутренние файлы директории.

Если `index.ts` содержит только реэкспорты, отдельный тест для него не нужен. Тестировать нужно файлы, в которых находится логика.

## Импорты в тестах

Модульные тесты должны импортировать код из конкретного файла, который они проверяют.

Допустимо:

```ts
import { renderCliHelp, isHelpRequested } from './help';
```

Запрещено для модульного теста конкретного файла:

```ts
import { renderCliHelp } from './index';
import { renderCliHelp } from '../help';
```

Второй пример запрещён, если `../help` разрешается как директория или модуль реэкспортов, а не как конкретный файл.

Интеграционный тест может идти через публичную точку входа, если проверяет её наблюдаемое поведение: код завершения, stdout/stderr, выбор команды, связывание зависимостей или контракт публичного API.

## Изоляция

Тест должен минимизировать зависимость от:

- реальной файловой системы, если проверяется не работа с ней;
- сети;
- текущего времени;
- порядка запуска тестов;
- внешних процессов;
- глобального изменяемого состояния;
- устаревших результатов сборки.

Если тест по смыслу зависит от внешнего ресурса, это должно быть ясно из имени теста, группы тестов или подготовленных данных и окружения.

## Тестовые данные

Тестовые данные должны быть минимальными, но достаточными для сценария.

Не нужно создавать реалистичный набор данных, если для проверки достаточно одного объекта с тремя полями.

Лишние поля скрывают причину теста и увеличивают стоимость сопровождения.

## Именование test suite

Имена тестов должны описывать путь публичного API и ожидаемое поведение.

Верхний `describe()` называет проверяемую сущность:

- `ClassName` для классов и компонентов времени выполнения;
- `functionName` для самостоятельных экспортируемых функций;
- `objectName` для экспортируемых объектов или пространств имён;
- `module-name` только когда тестируется несколько тесно связанных экспортов и нет одной основной проверяемой сущности.

## Именование nested suite

Вложенный `describe()` называет публичный член или операцию:

- `constructor` для поведения конструктора;
- `#methodName` для методов экземпляра, вызываемых как `instance.methodName()`;
- `.methodName` для статических методов, вызываемых как `ClassName.methodName()`;
- `.methodName` для методов экспортируемого объекта или пространства имён, вызываемых как `objectName.methodName()`;
- `functionName` для самостоятельных функций, объединённых в группу тестов модуля.

Примеры:

```ts
describe('UnaryLimitResolver', () => {
  describe('#resolve', () => {
    // ...
  });

  describe('#reduce', () => {
    // ...
  });
});

describe('command options', () => {
  describe('parseDateTimeOption', () => {
    // ...
  });
});
```

В одной родительской группе не должно быть соседних блоков `describe()` с одинаковыми именами. Объедините такие блоки или назовите их по разным публичным сценариям.

## Именование test case

`test()` называет только ожидаемое поведение.

Имя теста не должно повторять проверяемую сущность или имя метода, если они уже указаны в `describe()`.

Повтор проверяемой сущности удлиняет имя и ухудшает читаемость результатов тестирования.

## Предпочтительные behavior verbs

Предпочтительные глаголы для `test()`:

- `returns ...`;
- `throws ...`;
- `rejects ...`;
- `parses ...`;
- `formats ...`;
- `writes ...`;
- `reads ...`;
- `keeps ...`;
- `skips ...`;
- `uses ...`;
- `does not ...`;
- `handles ...`;
- `preserves ...`;
- `computes ...`;
- `maps ...`;
- `normalizes ...`;
- `ignores ...`.

`should` технически допустим, но прямое описание наблюдаемого поведения без лишнего модального слова читается лучше.

## Публичное поведение вместо private implementation

Обычно не создавайте отдельные группы тестов для деталей приватной реализации.

Приватные детали нужно тестировать через публичное поведение.

Исключение действует только для переиспользуемых вспомогательных сущностей, экспортируемых как часть контракта модуля. Проверяйте их наблюдаемое поведение, а не приватную реализацию.

## Error cases и boundary cases

Переиспользуемый код должен иметь тесты на успешные, ошибочные и граничные сценарии.

Особенно важно тестировать:

- пустые входные данные;
- минимально допустимые входные данные;
- максимально допустимые входные данные;
- неверный формат;
- неподдерживаемое значение перечисления;
- отсутствие обязательного поля;
- дублирующиеся входные данные;
- входные данные в неверном порядке;
- повторный вызов;
- идемпотентность;
- резервный сценарий;
- преобразование ошибки;
- пропущенную ветвь.

Не каждому модулю нужны все эти сценарии. Выбирайте только те, которые соответствуют его ответственности.

## Regression tests

Добавляйте регрессионный тест, если поведение уже ломалось или риск повторного дефекта высок.

Регрессионный тест должен фиксировать контракт рабочего кода, а не конкретную старую ошибочную реализацию.

Контекст регрессионного сценария можно раскрыть комментарием, если без него причина теста неочевидна.

## Комментарии в тестах

Комментарии в тестах регулируются отдельным документом:

- [Политика комментариев в тестах](./test-comment-style.md)

Краткое правило:

> Комментарий в тесте нужен только тогда, когда он объясняет риск ошибки при работе SDK, регрессионный сценарий, неочевидную подготовку теста, странное ожидаемое значение или границу ответственности теста.

Комментарий не должен пересказывать подготовку, выполнение и проверку теста или дублировать его имя.

Если комментарий можно заменить хорошим именем теста, улучшите имя вместо добавления комментария.

## Связь с изменениями

Добавляйте и меняйте тесты только в пределах задачи.

Запрещено:

- переписывать соседние тесты без необходимости;
- менять сценарий запуска тестов без явного запроса;
- переименовывать не связанные с задачей группы тестов "по пути";
- добавлять широкую очистку вместе с точечным регрессионным тестом;
- фиксировать новую архитектуру тестами, если задача была про локальный дефект.

Допустимо:

- добавить минимальный тест под новое требование;
- добавить регрессионный тест под исправляемый дефект;
- переименовать тест, если текущее имя мешает понять проверяемое поведение;
- локально улучшить подготовку данных и окружения, если без этого тест не выражает сценарий.

## Хорошие практики

- называть тест по наблюдаемому поведению, а не по внутренней реализации;
- держать тестовые данные минимальными, но достаточными для сценария;
- добавлять тесты на граничные и ошибочные случаи для переиспользуемой логики;
- избегать абстракций только для тестов без необходимости;
- не проверять несколько независимых поведений одним тестом;
- не использовать снимки или эталонный вывод без явного обоснования контрактом;
- не делать тест зависимым от порядка запуска других тестов;
- не использовать рабочие учётные данные, реальную сеть или изменяемое внешнее состояние;
- предпочитать явное ожидаемое значение вместо проверки "не упало";
- не хранить не относящиеся к задаче скомпилированные тестовые файлы внутри `dist`.

## Общий критерий

Хороший тест:

- защищает конкретный production contract;
- имеет понятный subject через `describe()`;
- имеет behavior-oriented имя через `test()`;
- использует минимальные данные;
- не зависит от случайного состояния окружения;
- проверяет публичное поведение;
- не фиксирует private implementation без необходимости.

Если тест сложно назвать, скорее всего, он проверяет слишком много или не имеет ясного contract.
