# Архитектурная политика

> Type: Policy. Этот документ задает ограничения на направление зависимостей, границы слоев и правила размещения файлов.

Проект использует Clean Architecture Lite.

Зависимости направлены внутрь.

```text
Domain
↑
Application
↑
Infrastructure
↑
Bootstrap
```

Это означает:

- `domain` не знает о внешнем мире;
- `application` координирует сценарии и зависит от абстракций;
- `infrastructure` реализует технические детали и внешние интеграции;
- `bootstrap` собирает runtime-зависимости и entrypoints.

Текущий SDK компактный и выделяет только те директории, у которых есть реальная
ответственность. Фактическая карта слоев описана в
[архитектуре SDK](../architecture.md).

Если слой еще не выделен в файловой структуре, правило направления зависимостей
все равно действует на уровне ответственности модулей.

## Направление зависимостей

Запрещено:

- нарушать направление зависимостей;
- импортировать внешний слой во внутренний;
- добавлять transport/provider/filesystem details во внутреннюю логику;
- переносить код между слоями без архитектурной причины;
- упрощать архитектуру через смешивание ответственностей;
- переносить SDK runtime wiring в modules, которые должны оставаться чистыми.

Допустимо:

- `infrastructure` реализует интерфейс, объявленный в `application` или `domain`;
- `bootstrap` собирает зависимости и передает их во внутренние слои;
- `application` координирует use case, не зная деталей gRPC, generated service definitions, filesystem или environment;
- `domain` содержит чистые правила, вычисления и модели предметной области.

Недопустимо:

- импортировать `infrastructure` в `domain`;
- импортировать `bootstrap` во внутренние слои;
- помещать код инициализации окружения во внутреннюю логику;
- переносить business/domain rules в bootstrap;
- помещать provider-specific или filesystem-specific код в `domain`.

## Назначение слоев

### `domain`

Содержит чистую предметную логику.

Здесь допустимы:

- модели предметной области;
- правила и политики, не зависящие от transport;
- чистые вычисления;
- domain-specific validators и converters.

Здесь не должно быть:

- gRPC, `nice-grpc`, metadata, channel, generated service client creation;
- чтения env/config;
- filesystem IO;
- форматирования пользовательского вывода;
- orchestration use-case-ов;
- generic helpers без предметного смысла.

### `application`

Содержит сценарии и контракты приложения.

Здесь допустимы:

- use-case-ы;
- application services;
- ports;
- DTO;
- report/output contracts;
- сценарные ошибки;
- orchestration между domain-логикой и ports.

Здесь не должно быть:

- прямой работы с `nice-grpc`, filesystem или внешними API;
- transport-specific mapping;
- provider-specific wiring;
- чистой domain-логики, если она может жить в `domain`.

### `infrastructure`

Содержит реализацию внешнего мира.

Здесь допустимы:

- gRPC adapters;
- SDK client creation;
- metadata/channel/middleware integration;
- generated service definitions;
- filesystem IO;
- external provider integration;
- serialization/deserialization внешних форматов.

Здесь не должно быть:

- business/domain rules;
- сценарных решений use-case-ов;
- чистой domain-логики.

### `bootstrap`

Содержит сборку и запуск runtime entrypoints.

Здесь допустимы:

- composition root;
- config resolving;
- связывание application contracts с infrastructure adapters;
- entrypoint wiring.

Здесь не должно быть:

- domain-вычислений;
- business rules;
- прямой реализации reusable ports;
- логики, которую можно переиспользовать вне запуска приложения.

### `internal`

Содержит внутренние generic utilities, которые не являются предметной областью.

Здесь допустимы:

- generic guards;
- generic formatting helpers;
- low-level helpers;
- технические функции без domain language.

Здесь не должно быть:

- business/domain rules;
- use-case orchestration;
- provider-specific кода.

### `generated`

Содержит код, полученный из upstream proto contracts
`contracts/t_tech/invest/grpc/**/*.proto`.

Здесь допустимы:

- generated TypeScript types;
- generated enum'ы;
- generated service definitions;
- код, воспроизводимый через proto workflow.

Здесь не должно быть:

- ручных правок;
- handwritten business logic;
- test-only helpers;
- project-specific wrappers.

## Правило размещения файлов

Перед созданием, переносом или переименованием файла необходимо определить его слой:

- `domain`;
- `application`;
- `infrastructure`;
- executable entrypoints в `bootstrap/bin`, bootstrap CLI mechanics в `bootstrap/cli/**` и command-level entrypoints вроде `bootstrap/commands/*/cli.ts`;
- `internal`;
- `generated`;
- `docs`;
- `contracts`;
- `dist`.

Файл нельзя размещать по принципу "где удобнее" или "рядом с похожим кодом", если это нарушает назначение слоя.

Если слой нельзя определить однозначно, изменение считается архитектурно неоднозначным. В этом случае нужно остановиться и запросить уточнение, а не создавать файл интуитивно.

## Правило создания директорий

Создание новой директории является архитектурным изменением.

Новая директория допустима только если:

- задача явно требует новую директорию;
- директория уже описана в архитектурной документации;
- изменение одновременно добавляет или обновляет документацию, объясняющую роль директории.

Запрещено создавать директорию только для удобной группировки файлов.

Запрещены новые generic-директории без явной архитектурной роли:

- `utils`;
- `helpers`;
- `common`;
- `shared`;
- `misc`;
- `wiring`;
- `lib`.

Если такая директория уже существует, это не является разрешением добавлять туда новый код. Сначала нужно проверить, не является ли директория техническим долгом.

## Правило `index.ts`

`index.ts` внутри директории является импортным фасадом.

В обычном случае `index.ts` должен содержать только re-export-ы и не должен
содержать runtime-логику:

- branching;
- parsing;
- validation;
- fallback behavior;
- command dispatch;
- formatting;
- wiring зависимостей.

Исключения допустимы только для явно определенных entrypoint-файлов, например
`src/index.ts`, или для редкого documented workaround, где `index.ts` является
неотъемлемой частью внешнего runtime-контракта.

Если в `index.ts` появляется поведение, его нужно вынести в файл с явной ролью.
Если `index.ts` не нужен как public import facade, его лучше удалить.

## Правило единственной точки входа модуля

У модуля не должно быть двух конкурирующих точек входа в одну и ту же сущность.

Плохой сигнал:

```text
feature/
  index.ts
  feature.ts
```

Если `feature/index.ts` и `feature/feature.ts` оба представляют сущность
`feature`, нужно
оставить один вариант:

- удалить `index.ts` и импортировать конкретные файлы;
- переименовать директорию;
- переименовать файл сущности так, чтобы он отражал отдельную роль.

Нельзя сохранять дублирование только ради короткого import path.

## Правило `types.ts`

`types.ts` не должен появляться автоматически только потому, что в модуле есть
TypeScript-типы.

Тип нужно держать рядом с владельцем контракта:

- рядом с registry, если тип описывает форму registry;
- рядом с mapper/renderer, если тип нужен только этому файлу;
- рядом с public API, если тип является частью public API.

Отдельный `types.ts` допустим, если типы:

- используются несколькими независимыми файлами и у них нет очевидного владельца;
- являются стабильным public/module contract;
- нужны для разрыва реального dependency cycle;
- описывают внешний контракт, а не локальную форму данных.

Если тип используется одним модулем или естественно принадлежит одному registry,
report, command или adapter, отдельный `types.ts` считается преждевременным
выделением.

## Правило именования файлов

Имя файла должно отражать его архитектурную роль.

Для новых файлов нужно использовать существующие project suffixes, если они подходят:

- `*.service.ts` - application/domain service;
- `*.port.ts` - application port;
- `*.report.ts` - application report/output contract;
- `reporter.ts` внутри `bootstrap/commands/<command>` - bootstrap presentation reporter;
- `*-renderer.ts` внутри `infrastructure/renderers` - механический renderer
  готовых значений в конкретный текстовый формат;
- `*-writer.ts` внутри `infrastructure/output` - технический sink для записи
  готового текста;
- `*.policy.ts` - правило или политика;
- `*.validator.ts` - validator;
- `*.mapper.ts` - mapper между слоями или форматами;
- `*.middleware.ts` - middleware;
- `*.adapter.ts` - infrastructure adapter;
- `*.test.ts` - тест.

Если ни один suffix не подходит, это сигнал, что роль файла не определена. В таком случае нужно сначала определить роль, а не придумывать новое абстрактное имя.

Запрещено использовать неочевидные авторские имена, если без чтения реализации нельзя понять назначение файла.

## Правило перемещения файлов

Перемещение файла между слоями допустимо только при наличии причины.

Допустимые причины:

- файл находится в неправильном слое;
- файл содержит логику, принадлежащую другому слою;
- файл нарушает направление зависимостей;
- файл является generic utility и ошибочно находится в `domain`;
- файл является infrastructure detail и ошибочно находится во внутреннем слое;
- файл является business/domain logic и ошибочно находится в `bootstrap` или `infrastructure`.

Недопустимые причины:

- "так красивее";
- "так короче import";
- "так удобнее сгруппировать";
- "рядом уже есть похожий файл";
- "можно уменьшить количество директорий".

## Правило минимального изменения

Архитектурный рефакторинг должен быть минимальным.

Запрещено в одном изменении одновременно:

- переносить файлы;
- переименовывать сущности;
- менять public API;
- менять поведение;
- переписывать реализацию;
- менять test pipeline.

Если требуется несколько типов изменений, они выполняются отдельными шагами.

## Сначала уточнение

Если изменение затрагивает слой, директорию, имя файла или направление зависимости, и правильное решение неочевидно, нужно сначала уточнить архитектурное намерение.

Запрещено угадывать placement.

Лучше остановиться и задать вопрос, чем создать файл в неправильном месте.

## Хорошие практики

- новые зависимости сначала проверять на соответствие направлению слоев;
- business/domain rules оставлять в слоях, где они уже живут по архитектуре;
- интеграционные детали локализовать в `infrastructure` и `bootstrap`;
- generic utilities не помещать в `domain`;
- generated code менять только через proto workflow;
- перед созданием файла проверять существующие naming patterns;
- перед созданием директории проверять, описана ли она в архитектурной документации;
- спорные изменения оформлять как отдельный маленький refactoring step.
