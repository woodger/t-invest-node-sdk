# Политика зависимостей

> Type: Policy. Здесь описаны критерии выбора библиотек и признаки нежелательных зависимостей.

Разрешены только качественные библиотеки.

Библиотека должна:

- решать широкую задачу
- иметь понятный API
- быть поддерживаемой
- давать архитектурную пользу
- быть оправданной долгосрочно

Нежелательные зависимости:

- пакет ради одной функции
- пакет ради удаления файлов
- пакет ради мелкой утилиты
- пакет-обёртка над стандартной функцией

Плохой пример:

rimraf

Хороший пример:

универсальная библиотека файловой системы с полноценным API

## Примеры выбора

Допустимо:

- добавить библиотеку, которая закрывает устойчивую инфраструктурную задачу и уже нужна в нескольких местах
- выбрать зависимость с ясной моделью поддержки и внятной документацией
- предпочесть стандартную библиотеку, если она покрывает задачу без архитектурных потерь

Недопустимо:

- добавлять пакет только ради одного вызова, который занимает несколько строк собственного кода
- тянуть зависимость ради "более красивого" синтаксиса
- добавлять библиотеку, если она дублирует уже используемый в проекте инструмент

## Хорошие практики

- перед добавлением зависимости формулировать, какую долгосрочную задачу она решает
- проверять, можно ли закрыть задачу существующими библиотеками проекта
- оценивать не только удобство API, но и стоимость сопровождения зависимости

## Lockfile

Проект поддерживает только `npm`. Не используйте Yarn, pnpm, Bun и другие менеджеры пакетов.

`package-lock.json` хранится в Git для воспроизводимых development- и CI-установок, но исключается из package archive через `.npmignore`: lockfile SDK не должен управлять разрешением зависимостей Consumer-проекта.
