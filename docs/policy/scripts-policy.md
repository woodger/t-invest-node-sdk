# Политика скриптов и сборки

> Type: Policy. Здесь описаны ограничения на изменение скриптов, сборки и порядка запуска тестов.

Скрипты сборки, тестирования и запуска считаются частью рабочего процесса проекта.

Они не должны изменяться без явной необходимости.

Запрещено:

- добавлять удаление файлов
- добавлять очистку dist
- добавлять `clean`-script для автоматической очистки перед `build` или `test`
- добавлять rm / fs.rmSync / rimraf
- добавлять prebuild / postbuild
- добавлять pretest / posttest
- менять порядок команд
- добавлять &&
- заменять node-логику shell-командами

Пример правильного скрипта:

"build": "tsc"

Пример неправильного изменения:

"build": "rm -rf dist && tsc"

Также запрещено:

```json
{
  "clean": "rm -rf dist",
  "build": "npm run clean && tsc",
  "test": "npm run clean && fwa",
  "prebuild": "rm -rf dist",
  "pretest": "rm -rf dist"
}
```

Исключение: скрипт `test` может передавать штатный флаг инструмента тестирования `fwa --prune`. Он удаляет только скомпилированные тесты без соответствующих исходных файлов при проверке порядка запуска тестов. Это не замена скрипта `clean` и не основание для общей очистки `dist`.

Если после перемещения файлов в `dist` остались устаревшие результаты сборки, удалите их явно и только при выполнении этой операции. Не меняйте ради этого постоянный порядок сборки и запуска тестов проекта.

Удаляйте файлы только по прямому требованию задачи.

## Дополнительные примеры

Допустимо:

- оставить существующий `build` без изменений и исправить причину ошибки в коде
- добавить новый скрипт только если задача прямо требует новую точку входа
- менять реализацию вызываемого файла, не меняя сам сценарий запуска, если задача про поведение этого файла

Недопустимо:

- `"test": "npm run lint && vitest"` вместо существующего `"test": "vitest"`
- `"build": "node scripts/build.js"` вместо существующего `"build": "tsc"` без прямого требования задачи
- добавлять очистку временных директорий "на всякий случай"
- добавлять автоматическую очистку `dist` перед `build` или `test`

## Хорошие практики

- рассматривать скрипты как часть контракта проекта, а не как служебную деталь
- если проблема решается внутри кода, не переносить решение в shell-команды
- перед изменением скрипта проверять, не меняется ли порядок шагов, побочные эффекты и точки входа
