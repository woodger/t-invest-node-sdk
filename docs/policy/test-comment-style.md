## Общее правило

Сначала дайте `describe()` и `test()` ясные имена. Если комментарий можно заменить хорошим именем, улучшите имя. Комментарий нужен только для причины, риска или контракта, которые остаются неочевидными из имени и проверок теста.

Не пересказывайте следующую строку, подготовку, выполнение и проверку теста. Не дублируйте его имя, не объясняйте очевидные действия и синтаксис тестового фреймворка. Ожидаемое значение, которое ясно из входных данных, пояснения не требует.

## Когда комментарий в тесте нужен

| Что требует пояснения | Что объяснить |
| --- | --- |
| Инвариант рабочего кода, регрессионный сценарий или исторически хрупкое место | Какой риск защищает тест и почему выбран этот сценарий; ссылки только на старое исправление недостаточно. |
| Неочевидная подготовка или необычная fixture | Почему данные выбраны намеренно; объясняйте причину, а не тип данных. |
| Ожидаемое значение, похожее на произвольное число | Какой контракт задаёт это значение. |
| Ограничение внешнего API | Как оно определяет проверяемое поведение. |
| Mock, stub или fake | Почему поведение намеренно отличается от реального и как это влияет на границы теста; если всё ясно из имени и подготовки, комментарий не нужен. |
| Snapshot или golden output | Какой контракт он фиксирует. |
| Выбор поведения и граница ответственности | Почему проверяется именно это поведение. |
| Намеренно пропущенная соседняя ответственность | Укажите её на уровне сценария или рядом с подготовкой, чтобы будущие правки не расширили границы теста по ошибке. |

## Блок тестового сценария

Перед группой тестов, которая защищает важный контракт рабочего кода, можно добавить сценарный блок:

```ts
/**
 * Сценарий: <что проверяется>.
 *
 * Защищает:
 * - <production-инвариант 1>;
 * - <production-инвариант 2>;
 *
 * Не проверяет:
 * - <соседняя ответственность, которая должна тестироваться отдельно>.
 */
```

## Комментарий внутри теста

Добавляйте локальный комментарий только там, где без него теряется причина конкретной подготовки, ожидаемого результата или необычной проверки. Держите его рядом с этой причиной; не комментируйте каждую проверку.

Удаляйте комментарий, если после рефакторинга пояснение стало очевидным. Описывайте контракт и риск, а не шаг реализации.

## Блоки Given / When / Then

Комментарии `Given`, `When`, `Then` допустимы только в длинных тестах, где они улучшают читаемость. Это не обязательный шаблон. В коротких тестах не добавляйте такие комментарии: структура должна быть понятна из кода.

## Язык комментариев

Используйте тот же язык, что и в комментариях рабочего кода проекта. Допустимы устойчивые технические термины: regression, fixture, mock, stub, fake, snapshot, golden output, runtime, contract, mapping, fallback. Не переводите их искусственно, если перевод снижает точность.

## Запрещенные комментарии

Запрещены комментарии, которые:

- описывают временную историю изменения без смысла для рабочего кода;
- содержат TODO без привязки к issue, решению или решению владельца;
- оправдывают хрупкий тест вместо исправления его структуры;
- маскируют слишком большой тестовый сценарий.

Если тест требует такого комментария, сначала упростите подготовку или разделите сценарий. Комментарии не должны превращать тест в документацию по фреймворку.
