# Roadmap и рабочие идеи

> Type: Brainstorm. Здесь собраны идеи, а не утверждённый план, публичное обещание или согласованный контракт. До начала реализации любой вариант можно пересмотреть или отклонить.

## Межпроцессная координация unary-квот

### Контекст

По умолчанию ограничитель unary-запросов не подключен. Вы можете передать собственную реализацию или явно создать ограничитель для одного процесса. Два независимо созданных ограничителя не видят резервирования друг друга и каждый планирует вызовы по полной переданной квоте.

У команд, использующих разные сервисы провайдера, квоты сервисов могут не пересекаться. Однако процессы всё равно участвуют в общих ограничениях пользователя и IP. Два процесса, вызывающие один сервис или методы одной группы квот, могут вместе превысить лимит провайдера. Актуальную модель и известные границы локального ограничителя описывает [лимитная политика](./limits-policy.md).

Актуальные источники:

- публичный интерфейс и необязательная реализация для одного процесса — [`src/application/services/unary-limiter.ts`](https://github.com/woodger/t-invest-node-sdk/blob/main/src/application/services/unary-limiter.ts);
- подключение ограничителя приложения — [`src/bootstrap/t-invest-node-sdk.ts`](https://github.com/woodger/t-invest-node-sdk/blob/main/src/bootstrap/t-invest-node-sdk.ts);
- сопоставление RPC с общим `bucket` квоты — [`src/infrastructure/transport/grpc/unary-limit-resolver.ts`](https://github.com/woodger/t-invest-node-sdk/blob/main/src/infrastructure/transport/grpc/unary-limit-resolver.ts).

### Термины, которые нельзя смешивать

`bucket` — заданный SDK идентификатор квоты провайдера. Например, один `bucket` объединяет вызовы по общему правилу сервиса, а другой — методы явно объявленной группы квот. Он не идентифицирует приложение, пользователя или процесс.

Область координации определяет, какие экземпляры SDK должны делить состояние: один пользователь T-Invest и окружение, одна точка выхода в сеть или всё конкретное развёртывание.

Также различаются два механизма:

- блокировка задач запрещает одновременное выполнение несовместимых операций синхронизации;
- ограничитель частоты запросов разрешает параллельную работу, но координирует частоту RPC.

Ограничитель частоты запросов не предотвращает дублирование синхронизации, гонки записи и повторную обработку данных. Если параллельный запуск сам по себе недопустим, нужна блокировка задач или единый владелец очереди независимо от координации квот.

### Вариант: один долгоживущий sync-worker в приложении

Приложение может заменить независимое выполнение CLI-команд одним процессом, который владеет экземпляром SDK и очередью задач синхронизации:

```text
CLI / scheduler
  -> sync-worker
       -> candles sync
       -> instruments sync
       -> один SDK lifecycle и один набор quota counters
```

Преимущества:

- не нужны новое хранилище и межпроцессное состояние ограничителя;
- один планировщик координирует все вызовы SDK;
- в одном месте решаются повторный запуск, порядок задач, отмена, корректное завершение работы и обработка `RESOURCE_EXHAUSTED`;
- не требуется отдельно управлять внешним хранилищем или сервисом ограничителя.

Ограничения:

- приложение должно управлять временем жизни долгоживущего воркера;
- CLI становится клиентом воркера или простым способом поставить задачу;
- протокол постановки задачи и доставки результата становится контрактом приложения.

Для текущего сценария это основной кандидат: он снимает риск превышения квот и проблему одновременного выполнения операций синхронизации.

### Вариант: локальный IPC coordinator

Если независимые CLI-процессы должны сами выполнять вызовы SDK, на одной машине можно запустить отдельный координатор с общим планировщиком в памяти. Клиенты будут запрашивать разрешения через Unix domain socket или именованный канал Windows.

Предполагаемые свойства:

- координатор запускается и контролируется явно через диспетчер процессов;
- процессы SDK не пытаются автоматически выбрать лидера или породить скрытую фоновую службу;
- OAuth-токен не передаётся по IPC и не используется как ключ `bucket`;
- одна точка подключения IPC может соответствовать одной явно определённой области координации;
- разрыв соединения или `AbortSignal` удаляет из очереди запрос, которому ещё не выдано разрешение;
- после выдачи разрешения слот не возвращается, поскольку провайдер уже мог учесть вызов;
- при недоступности координатора запросы не разрешаются; локальный ограничитель не подменяет общую координацию;
- решение ограничено одной машиной или общим пространством имён IPC.

Без постоянного хранения состояния после аварийного перезапуска координатор не знает о недавних запросах, уже учтённых провайдером. Поэтому перед выдачей новых разрешений придётся ждать не меньше полного временного окна квоты. Это осознанная плата за отсутствие базы данных.

### Реализованная граница: injectable limiter contract

SDK предоставляет интерфейс ограничителя, не зависящий от конкретного хранилища или сервиса. Публичные типы, выбор `bucket` квоты, отмена, управление временем жизни, ошибки и исключение потоков из unary-контракта описаны в [руководстве по собственной реализации ограничителя](./guides/custom-unary-limiter.md).

Один интерфейс не решает межпроцессную координацию. Встроенный ограничитель поддерживает `quotaShare` для явного статического выделения доли при заранее известном числе независимых ограничителей. Он не обнаруживает изменение их состава и не перераспределяет свободную квоту. Для динамической координации по-прежнему нужен координатор и его интеграционные тесты. Ниже сохранены рассмотренные варианты такой реализации.

### Вариант: Redis или другое общее хранилище

Один из рассмотренных вариантов — внешний координатор на базе Redis с атомарной выдачей разрешений, общими ключами `bucket` квот, отменой и TTL. Он может координировать процессы на разных машинах и работать независимо от времени жизни отдельных процессов CLI.

Для текущего проекта этот вариант исключён: Redis, SQL или другая база данных не должны становиться инфраструктурным требованием SDK или приложения только ради координации квот. Не нужно добавлять зависимость от Redis, необязательный динамический импорт или неявное переключение на сетевое решение.

Вернуться к этому варианту имеет смысл, только если появятся готовая общая инфраструктурная платформа и реальная потребность в нескольких машинах. Даже тогда хранилище или сервис должны остаться реализацией внешнего интерфейса, а не частью преобразований данных провайдера или правил планирования приложения в SDK.

### Рассмотренные упрощения

Следующие варианты не считаются полноценным общим ограничителем:

- независимые счётчики в памяти каждого процесса — не координируют суммарную нагрузку;
- статическое деление лимита между предполагаемым числом процессов — доступно через `createInMemoryUnaryLimiter({ quotaShare })`, но не считается полноценной координацией: оно ломается при изменении числа параллельных процессов и неэффективно использует свободную квоту;
- файл блокировки с JSON-состоянием — требует обработки устаревших блокировок, аварий процессов, повторного использования PID, атомарной записи, отмены и переносимости;
- краткоживущая блокировка файловой системы вокруг одного RPC — сериализует критическую секцию, но не хранит корректный временной график;
- автоматическая фоновая служба, создаваемая первым CLI-процессом, — имеет неоднозначные правила владения, завершения, обновления и восстановления;
- один мьютекс задач — предотвращает одновременное выполнение задач, но не координирует квоты между разрешёнными параллельными работами.

### Инварианты возможной реализации

Если к задаче вернутся, до изменения публичного API нужно зафиксировать:

1. Точную границу: одна машина или несколько машин.
2. Владельца процесса координатора и порядок его запуска и завершения.
3. Стабильную область координации без использования самого OAuth-токена.
4. Стабильную идентичность значений `bucket`, сформированных SDK.
5. FIFO, отмену и правило отсутствия возврата квоты после выдачи разрешения.
6. Запрет выдачи разрешений при потере координатора.
7. Правила запуска после потери состояния, которое хранилось только в памяти.
8. Отдельную модель квот сервисов, пользователей и общих ограничений IP.
9. Поведение при разных `unaryLimits` у одновременно работающих процессов.
10. Интеграционные тесты с реальными дочерними процессами, включая аварийное завершение и перезапуск.

### Текущее решение

SDK не реализует межпроцессный ограничитель. Публичный интерфейс позволяет приложению подключить координатор без изменения таблицы квот SDK, но не определяет, как он должен работать. `quotaShare` остаётся ручным статическим распределением, а не скрытым механизмом обнаружения процессов.

Один долгоживущий воркер синхронизации остаётся отдельным вариантом. Локальный координатор IPC возможен, если нужно сохранить независимые CLI-процессы и все они работают на одной машине. Redis и другие базы данных исключены из текущего направления.
